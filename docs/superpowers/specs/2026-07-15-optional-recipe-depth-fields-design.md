# Optional min_depth/max_depth in Recipes Design

**Date:** 2026-07-15
**Status:** Design phase
**Context:** `ValidationDataSource.min_depth`/`max_depth` currently default to concrete floats (-20.0/20.0), so every validation source — including source types that never use a depth filter (scatterometer, altimeter, radiometer) — carries and serializes a depth range whether or not it was ever requested.

---

## Overview

`ValidationDataSource` (in [`sar_validation/core/recipe.py`](../../../sar_validation/core/recipe.py)) declares:

```python
min_depth: float = -20.0
max_depth: float = 20.0
```

Because these are required-with-default dataclass fields (not `Optional`), three things happen today regardless of what a recipe author actually wants:

1. `Recipe._from_dict()` always resolves an unspecified `min_depth`/`max_depth` in YAML/JSON to a concrete `-20.0`/`20.0`.
2. `Recipe.to_yaml()`/`to_json()` always serialize `min_depth: -20.0` / `max_depth: 20.0` for every validation source, including ones (e.g. `scatterometer`, `altimeter`, `radiometer`) where depth is meaningless.
3. `HFRadarDownloader`'s own constructor default (`-2.0`/`2.0`) is silently dead when driven through a recipe, because `orchestrator.py` always passes the recipe's already-resolved `-20.0`/`20.0` — a discrepancy that's currently invisible.

Goal: a recipe that doesn't care about depth should not mention `min_depth`/`max_depth` at all — neither when hand-written nor when generated by `Recipe.to_yaml()`/`to_json()`. When depth is unspecified anywhere in the pipeline, the effective value used for the Copernicus Marine download is `-20`/`20`.

---

## Data Model

`min_depth`/`max_depth` become `Optional[float] = None` on `ValidationDataSource`, for all source types (no per-type branching):

```python
@dataclass
class ValidationDataSource:
    source_type: str
    min_depth: Optional[float] = None
    max_depth: Optional[float] = None
    download_kwargs: Dict[str, Any] = field(default_factory=dict)
    collocation_kwargs: Dict[str, Any] = field(default_factory=dict)
```

Two module-level constants in `recipe.py` hold the single source of truth for the fallback:

```python
DEFAULT_MIN_DEPTH = -20.0
DEFAULT_MAX_DEPTH = 20.0
```

`ValidationDataSource` gains two read-only properties that resolve the effective depth for callers, so the `None` → default logic lives in exactly one place:

```python
@property
def resolved_min_depth(self) -> float:
    return self.min_depth if self.min_depth is not None else DEFAULT_MIN_DEPTH

@property
def resolved_max_depth(self) -> float:
    return self.max_depth if self.max_depth is not None else DEFAULT_MAX_DEPTH
```

---

## Serialization

`ValidationDataSource.to_dict()` currently delegates to `asdict(self)`, which would emit `min_depth: null`/`max_depth: null` for every unspecified source — not what we want. It becomes a manual dict build that omits the keys entirely when `None`:

```python
def to_dict(self) -> Dict[str, Any]:
    d: Dict[str, Any] = {"source_type": self.source_type}
    if self.min_depth is not None:
        d["min_depth"] = self.min_depth
    if self.max_depth is not None:
        d["max_depth"] = self.max_depth
    d["download_kwargs"] = self.download_kwargs
    d["collocation_kwargs"] = self.collocation_kwargs
    return d
```

`Recipe._from_dict()` drops its forced default:

```python
# before
min_depth=src.get("min_depth", -20.0),
max_depth=src.get("max_depth",  20.0),

# after
min_depth=src.get("min_depth"),
max_depth=src.get("max_depth"),
```

Net effect: a recipe file that never mentions depth round-trips (`from_yaml` → `to_yaml`) without depth keys ever appearing. A recipe that explicitly overrides depth for one source (e.g. hf_radar at -2/2) keeps exactly that override and nothing else.

## Resolution at the point of use

`orchestrator.py` is the only other consumer of these fields, in two places. Both switch from reading the raw field to reading the resolved property:

**In-situ batch aggregation** ([orchestrator.py:109-110](../../../sar_validation/core/orchestrator.py#L109-L110)) — multiple in-situ sources share a single Copernicus Marine download call, so the code takes the most permissive depth window across all of them:

```python
# before
min_depth = min(s.min_depth for s in insitu_sources)
max_depth = max(s.max_depth for s in insitu_sources)

# after
min_depth = min(s.resolved_min_depth for s in insitu_sources)
max_depth = max(s.resolved_max_depth for s in insitu_sources)
```

Behavior is unchanged for sources that specify depth explicitly; sources that don't now contribute `-20`/`20` to the aggregation (same numeric outcome as today, just resolved later).

**HF radar dispatch** ([orchestrator.py:259-260](../../../sar_validation/core/orchestrator.py#L259-L260)):

```python
# before
min_depth=source.min_depth,
max_depth=source.max_depth,

# after
min_depth=source.resolved_min_depth,
max_depth=source.resolved_max_depth,
```

This is the one behavior change: an hf_radar recipe source that never specifies depth now resolves to `-20`/`20` (matching every other source type) instead of silently forcing `-20`/`20` via the old dataclass default (no functional difference today) — the difference only becomes visible if the dataclass default is ever removed in isolation. The important guarantee going forward: whatever HFRadarDownloader's own constructor default is, the recipe layer always wins when driven through a recipe.

---

## Out of scope

- **Downloader constructor defaults and standalone CLIs** (`InSituDownloader.__init__`, `HFRadarDownloader.__init__`, and each module's `_parse_args`/`main`) are untouched. They're a separate calling path — direct/standalone downloader invocation, not recipe-driven — and this change is scoped to recipes. `HFRadarDownloader`'s own default stays `-2.0`/`2.0` for that path.
- **`cli.py`'s recipe-template builders** (`_build_currents_config` and friends) need no code changes. They already omit `min_depth`/`max_depth` for sources that don't need an override (drifter, ferrybox, mooring, scatterometer, altimeter, radiometer, tidal_gauge) and only pass explicit values for hf_radar/hf_radar_noaa (-2.0/2.0, a deliberate override for near-surface HF radar measurements). Once the dataclass default changes to `None`, these templates automatically stop baking `-20.0`/`20.0` into generated recipes — no template edits needed.
